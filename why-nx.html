Nx 1.2 · the same job, two ways

What you write  vs.  what the language carries

Python and Nx, side by side. Watch the red — that's the work you do by hand in Python that Nx's one rule does for you.

Nx's whole idea is one rule: used paths get stronger, unused ones fade. That single rule shows up as three things you'd normally build yourself. Same results both sides — the difference is how much you have to write.

1 · Remembering answers (caching)

A function whose answer depends only on its input, called over and over — the classic example, Fibonacci.

Python

from functools import lru_cache

@lru_cache(maxsize=None)   # ← YOU add this line
def fib(n):
    return n if n < 2 else fib(n-1) + fib(n-2)

Without that line, fib(32) makes 7,049,155 calls (0.88s). You have to know to add it.

Nx

agent fib(n) {
  when n < 2 { report n }
  report fib(n-1) + fib(n-2)
}

No annotation. The language caches a hot, pure agent itself — fib(32) returns instantly. Same answer: 2178309.

2 · Sending work to the faster worker (load-balancing)

You have two workers that do the same job; one is faster. Push more of the work to the fast one.

Python

import time
# you write the balancer yourself:
def run(workers, items):
    weight = [1.0]*len(workers)
    out = [None]*len(items)
    for i, item in enumerate(items):
        w = pick_by_weight(weight)        # you write this
        t = time.time()
        out[i] = workers[w](item)
        weight[w] = faster(weight[w], time.time()-t)
    return out
# + pick_by_weight(), faster(), ...

You own the timing, the weighting, the loop — and the helpers it calls.

Nx

schedule("pool", [fast, slow], items)

flows("pool")
# -> { fast: 5.98, slow: 1.03 }

One line. The pool measures speed and sends more work to the fast tube — and remembers it for next time. (Real output above.)

3 · When a worker dies (failover)

One worker breaks mid-job. The work still has to get done.

Python

for i, item in enumerate(items):
    for w in by_health(workers):   # you write retry
        try:
            out[i] = w(item); break
        except Exception:
            mark_unhealthy(w)          # you write this

You write the retry, the health tracking, the reroute.

Nx

schedule("pool", [maybe_broken, ok], items)

# a dead worker decays;
# its items reroute to the survivors

The same one line. Failover is already in the scheduler — nothing extra to write.

The honest version (so I'm not overselling)

Nx is not faster than Python for everyday work — it's an interpreter, and for tight number-crunching Python wins. The point isn't speed. The point is the red: in Python you write the cache, the balancer, and the failover. In Nx, one rule — used paths strengthen, unused fade — carries all three, so that code simply isn't there.

And the part that earns its keep today isn't even the self-tuning — it's safety: an Nx program can only touch what you explicitly hand it. Nothing else exists in its world to misuse. That's the one you can hand to an AI.
